# aspnet-buildtools

npm package that generates Vite/Webpack entry points and import aliases from ASP.NET Core Razor views. ESM only, written in TypeScript, built to `dist/`.

## The three projects

This repo is one of three that work together:

- [aspnet-buildtools](https://github.com/Baune8D/aspnet-buildtools) (npm): generates Vite/Webpack entry points and aliases from Razor views.
- [AspNet.AssetManager](https://github.com/Baune8D/AspNet.AssetManager) (NuGet): reads the bundler manifest and renders `<script>`/`<link>` tags.
- [AspNet.Frontend.Templates](https://github.com/Baune8D/AspNet.Frontend.Templates) (NuGet): `dotnet new` templates that combine both.

- View bundle names (`Views/Home/Index.cshtml` → `Views_Home_Index`) are generated by aspnet-buildtools (`getEntryPoints`) and inferred by AspNet.AssetManager (`GetBundleName`). Change both together.
- After releasing AspNet.AssetManager or aspnet-buildtools, update the templates to the new version and release them too.

## Workflow

- Conventional commits (`feat:`, `fix:`, `chore(deps):`, `ci:`, `build:`, `docs:`), one commit per concern, directly on `main`.
- Only push, tag, publish or edit GitHub releases when asked.

## Releasing

- **NuGet packages:** push a lightweight tag `vX.Y.Z` on `main`. CI publishes to NuGet on tags. Every push to `main` also publishes a beta to MyGet.
- **npm package:** `npm version patch -m "%s"`, then `git push origin main --follow-tags`. Publishing needs a 2FA code, so the user runs `npm publish --otp=<code>`.
- **Verifying:** NuGet takes about 3-6 minutes before a new version can be installed. npm caches package metadata; use `--prefer-online`.
- **Versioning:** any change to a public interface (`IAssetService`, `IManifestService`, `ITagBuilder`, tag helper attributes, exported functions) is breaking and needs a major version. Several 4.x releases of AspNet.AssetManager shipped breaking changes as minor/patch versions; don't repeat that.

### GitHub release notes

Use these sections, omitting empty ones, and end with a compare link:

```markdown
## Breaking changes

## Features

## Fixes

## Known issues

## Other

**Full Changelog**: https://github.com/Baune8D/<repo>/compare/vA...vB
```

- Write for users of the package: name the exact APIs, settings and before/after values. Leave out internal changes (tests, CI, IDE files).
- For the templates, use "Changes in generated projects" instead of Features/Fixes.
- When a release fixes a bug from an earlier release, add a "Known issues" entry to the earlier release saying "Fixed in vX.Y.Z".

## Dependencies

- Dependabot runs weekly on Monday with a 7-day cooldown. Minor/patch updates are grouped; security updates have their own group.
- Major versions are ignored by Dependabot and upgraded by hand: read the release notes, update, and build/test before committing. If a major breaks the build and fixing it is a design decision, keep the old major and explain why in the commit.
- New exceptions go in `.github/dependabot.yml` with a comment explaining why.
- The AspNet.AssetManager demo and the templates mirror the default ASP.NET Core templates, so they stay on jQuery 3 (`jquery-validation-unobtrusive` also requires it).

## Building and testing

`npm run lint`, `npm test` and `npm run build`. CI runs all three on Node.js 22 and 24.

## Constraints

- Requires Vite 8+: the config uses `build.rolldownOptions` (Vite 8 still accepts `rollupOptions` as a deprecated alias). Users on Vite 7 or earlier need `aspnet-buildtools@0.2`.
- TypeScript is capped at 6.0 because typescript-eslint and ts-jest don't support 7 yet.
- `@types/node` follows the minimum supported Node.js version (`engines.node`, currently 22). Dependabot ignores its major updates.
- `tsconfig.build.json` must set `rootDir: "src"`; without it TypeScript 6 writes the output to `dist/src/` and breaks `main`.
- After a dependency upgrade, compare `dist/` with the previous build to confirm the output didn't change.

## Behavior to keep in mind

- `viteConfig` and `webpackConfig` are built from `process.cwd()` when the module is loaded. The functions take an optional `context` instead.
- `viteDevManifestPlugin` serves the dev manifest at the `build.manifest` path. With `manifest: true` that is `/.vite/manifest.dev.json` while the production manifest is `.vite/manifest.json`, so AspNet.AssetManager's `ManifestFile` must differ per environment. The README recommends a fixed file name instead.
- The README's code examples should actually work. Test changes to them by building the `example/` folder with each config.
